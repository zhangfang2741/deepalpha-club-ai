# 量化研究 + 分析师评级（缠论 App 个股详情页）设计

> 日期：2026-09-30 · 状态：设计已确认，待写实施计划
> 草图：`.superpowers/brainstorm/34847-1790735482/content/`（`quant-full-v2.html`、`quant-drill-v4.html`、`quant-radar-v3.html`、`analyst-tab-v2.html`）
> 验证脚本与数据：`data/quant_seed/2026-09-30/`（git 忽略，约 100MB：7521 个 FMP 原始响应 + 成分表 + 脚本 + 报告；结论见附录 A）

## 1. 目标与范围

在缠论 App（`ios/DeepAlphaChan`）个股分析详情页，参照 Seeking Alpha 的 Quant 因子评级，为美股提供**多维度、同行横向比较、每个数都能追到原始数据**的量化研究，并附带华尔街分析师评级。

**第一期范围**
- 详情页顶部新增分段：`缠论结构 | 量化研究 | 分析师评级`。「缠论结构」即现有整页，**不改动**。
- 量化研究：综合等级 + 五维度（估值 / 成长 / 盈利能力 / 动量 / EPS 修正）+ 三层下钻（首页 → 维度详情 → 指标详情）+ 五维图 + 阶段标注。
- 分析师评级：评级分布与趋势、目标价、业绩预期 vs 实际、最近评级变动。
- 仅美股。API 按多市场设计；A 股一致预期快照**第一期即开始每日落库**（为二期 EPS 修正积累历史）。
- 后端新增全局 FMP 限流器（Redis 令牌桶）。

**不在第一期**
- 信号雷达接入量化维度（已讨论方向：缠论分 × 量化同向加权，不加排序胶囊；另立设计）。
- 港股 / A 股的量化研究（二期，数据源 akshare）。
- 等级历史页、等级变化原因说明、市值/风险调整、按阶段区分指标或权重、回测校准因子权重（第一期的每日存档为这些做准备）。
- 第六维度「财务健康」、股息评分。

## 2. 用语与合规规则（有测试守护）

1. 模块名「量化研究」；综合结果叫「综合等级」，用字母 A+ ~ F，**不出现**买入 / 卖出 / 推荐 / 看多 / 看空 / 强力 / 上涨空间 等买卖导向措辞。
2. 「主要依据」只写客观对比：「前瞻市盈率 41.2，高于板块 88% 的公司」，不写「偏贵」「谨慎」等判断。
3. 面向用户的文案**不出现数据供应商名**（FMP、akshare、东财等）；只展示时间（行情日、财报期与披露日、预期更新日）。API 响应不含 source 字段，来源只记服务端日志。
4. 分析师评级 Tab 中「买入 / 持有」等是**分析师原始评级标签**，只在该 Tab 以引述方式出现；我们生成的文案仍受第 1 条约束。「较现价 +41.9%」是算术差，不写「上涨空间」。
5. 页面底部免责：「量化研究为基于公开财务数据的统计比较，不构成投资建议。」
6. 后端测试：对所有生成文案做禁用词扫描（买卖导向词 + 供应商名），分析师评级的评级标签字段单独豁免。
7. 维度名称暂用专业名（估值 / 成长 / 盈利能力 / 动量 / EPS 修正）；通俗化命名为**待决事项**（见 §12）。

## 3. 方法口径（methodology_version = `q1`）

总体原则：**尽可能贴近 Seeking Alpha 公开的做法**；SA 未公开的部分取最可解释的方案并在方法说明页写明。

### 3.1 同行与比较基准
- 样本：标普 1500（S&P 500 + 400 + 600，约 1504 只），成分取自维基百科成分表（`pd.read_html`，同 `signal_radar/constituents.parse_wiki_sp500`），含 **GICS 板块**，每周刷新。
- 所有指标在 **GICS 板块内**比较（11 个板块，最小「通信服务」约 49 只）。页面写「与信息技术板块 138 家公司比」，不写「行业」。
- 样本外美股：用 FMP profile 的 sector 映射到 GICS 板块，按当日板块分布打分，不计入分布本身；排名写「相当于板块内第 x 位」。
- 横向比较只表示在同行中的相对位置；指标详情同时给出本股数值与板块中位数，用户能看到绝对水平。

### 3.2 单项指标
- 百分位 p ∈ [0,100]：板块内排名，方向统一为「越高越好」（估值类越便宜越高）。
- 同时展示「与板块中位数的差异 %」（SA 的展示方式）；**等级按百分位**（对极端值稳健）。
- 特殊值状态 `status`：
  - `ok`
  - `not_meaningful`：分母为负且确属「没有利润」（如亏损导致 PE < 0、EBIT < 0 导致 EV/EBIT 无意义）→ **按最差（p=0）计**，页面注明。
  - `not_applicable`：数值无意义但非经营不佳，如**回购导致股东权益为负**时的 ROE、市净率 → **不参与计算**，页面注明原因。
  - `missing`：数据缺失 → 不参与计算。
- 前瞻类指标：**NTM 口径**（按剩余月份对 FY1 / FY2 一致预期加权）；前瞻增速 = FY1 一致预期 ÷ **上一完整财年实际值** − 1（验证发现以 TTM 为分母会系统性低估 NVDA 这类已走过大半个财年的公司）。
- 一致预期覆盖 **< 3 位分析师**时，所有预期类指标记 `missing`。

### 3.3 等级分档（全模块同一把尺子，13 档）
`≥93 A+ · ≥86 A · ≥80 A- · ≥73 B+ · ≥66 B · ≥60 B- · ≥53 C+ · ≥46 C · ≥40 C- · ≥33 D+ · ≥26 D · ≥20 D- · <20 F`

**防抖动**：与上一交易日等级比较，只有百分位越过分档边界 **≥ 2 分**才改变等级，否则沿用旧等级（算式照常显示当日真实百分位）。适用于指标、维度、综合三层。

### 3.4 维度分
- 维度分 = 该维度内所有**参与计算**指标百分位的**等权平均**（验证：与分组等权相比平均只差 1.6~2.3 分，取更简单、更接近 SA 的全指标等权）。页面仍按组折叠展示（如「市盈率：TTM / 前瞻」一行）。
- 参与计算的指标不足该维度一半 → 维度 `unavailable`。

### 3.5 综合等级
1. 综合分 = 可用维度分的等权平均（SA 权重未公开；以后用自有存档回测校准）。
2. 综合分在标普 1500 全体中的百分位 → 同一把尺子换成字母等级。
3. **一票否决**：任一维度为 F（维度分 < 20）→ 综合等级最高 **C+**，页面说明原因。（SA 原门槛直译会让 65% 股票被封顶，不可用；「任一 F」触发约 28%。）
4. **无分析师覆盖（< 3 位）不给综合等级**（与 SA 一致），仅展示各维度。
5. EPS 修正处于积累期时，综合分由其余 4 个维度计算，页面写明「本次综合等级基于 4 个维度」。

### 3.6 指标清单（第一期）

| 维度 | 组（页面折叠行） | 指标 |
|---|---|---|
| 估值（越低越好） | 市盈率 | PE TTM、PE 前瞻 |
| | PEG | PEG TTM、PEG 前瞻 |
| | 市销率 | P/S TTM、P/S 前瞻 |
| | EV/营收 | TTM、前瞻 |
| | EV/EBITDA | TTM、前瞻 |
| | EV/EBIT | TTM、前瞻 |
| | 市净率 | P/B TTM |
| | 市现率 | P/经营现金流 TTM |
| 成长 | 营收 | 同比 TTM、前瞻、3 年复合 |
| | EBITDA | 同比 TTM、前瞻 |
| | EBIT | 同比 TTM、前瞻 |
| | EPS | 同比 TTM、前瞻 |
| 盈利能力 | — | 毛利率、EBIT 利润率、EBITDA 利润率、净利率、自由现金流利润率、ROE、ROA、ROIC、资产周转率（均 TTM） |
| 动量 | — | 3 / 6 / 9 / 12 个月涨幅（前复权，板块内比较） |
| EPS 修正 | — | FY1 EPS 一致预期 30 天、90 天变化；FY2 EPS 90 天变化；FY1 营收 90 天变化 |

- 变化率在负基数时用 `(新 − 旧) / |旧|`，亏损收窄算上修。
- EPS 修正依赖自有快照：上线满 30 天启用 30 天指标，满 90 天全部启用；之前维度状态为 `accumulating`（「修正历史积累中（已 x 天）」）。**与 SA 的差异**：SA 统计上修 / 下修的分析师人数，FMP 无逐分析师数据，改用一致预期均值变化；方法说明页写明。
- 增长类指标基数 ≤ 0 → `missing`（不是最差）。

### 3.7 阶段标注（Dickinson 现金流生命周期，只标注不改分）

按 TTM 经营 / 投资 / 筹资现金流符号：初创期（− − +）、成长期（+ − +）、成熟期（+ − −）、收缩期（− + ±）、其余为调整期。另加「尚未盈利」（TTM EPS ≤ 0）。
综合等级卡片显示小标签（如「成长期 · 尚未盈利」），点开给出三项现金流数值与判定规则，以及中性的「这一阶段常见的关注点是……」。

## 4. UI（iOS，缠论 App）

- `ResultDetailView` 导航栏下加三段分段控件；「缠论结构」为现有 `pageContent`。分享长图只截当前分段。
- **量化研究首页**（`quant-full-v2.html` 屏①）：
  1. 窄卡：综合等级 + 综合分 + 「标普1500 前 x%」+ 阶段标签 + 比较对象与数据时间（行情日 / 财报期）。
  2. 五张维度卡片，**固定顺序**（估值、成长、盈利能力、动量、EPS 修正），最高 / 最低两项加高亮边框；每张：等级、维度名、**关键事实**（该维度中最能代表其方向的指标：维度分 ≥ 50 取百分位最高者，否则取最低者）、板块百分位条（灰线 = 板块中位）、「查看 xx 的指标 ›」。
  3. 底部五维图：半径 = 百分位，实线本股、虚线板块中位（50）；点顶点进入该维度；不可用维度画灰色虚轴标「暂无」。轴标签按实际文字宽度布局并限制在画布内（草图曾出现左侧标签被裁）。文案称「五维图」，避免与「雷达」Tab 混淆。
  4. 「等级是怎么算的？」→ 方法说明页（服务端下发）。
- **维度详情**（新页面，屏②）：顶部展开算式「(12+9+…) ÷ n = 19.6 → D」；按组折叠列出指标：本股 / 板块中位 / 差异% / 百分位条 / 等级。
- **指标详情**（半屏 sheet，屏③）：定义 → 带真实数字的算式 → 板块分布 P10/P25/中位/P75/P90 与本股位置 → 「高于 x% 的同板块公司 → 百分位 → 等级」→ 原始数据及各自时间点、样本量、特殊值说明。
- **分析师评级**（`analyst-tab-v2.html`）：评级分布（五档人数 + 近 3 个月变化）、目标价（轴从 min(现价, 最低) 到 max，标现价 / 最低 / 中位 / 最高）、业绩预期 vs 实际（近 4 季 EPS 差异 + 下次披露日）、最近评级变动（机构 / 日期 / 动作 / 评级）。
- 港股 / A 股：量化研究与分析师评级显示「暂只支持美股」。
- 颜色沿用 App 红涨绿跌：A/B 红、C 灰、D/F 绿。

### 5.2 分析师评级（加入现有 `analyst_upgrade` 模块）

`GET /api/v1/analyst-upgrades/overview/{symbol}` — 实时请求，Redis 缓存 6h，经全局限流器。
- 评级分布与月度趋势：统一用 FMP `grades-historical`（**不混用** `grades-consensus`：两者口径不同，NVDA 同日 63 vs 79 家）。
- 目标价：`price-target-consensus`（最高 / 最低 / 中位 / 均值）+ `price-target-summary`（近月 / 季 / 年发布次数）。
- 业绩：`earnings`（近 4 季 EPS 实际 vs 预期、下次披露日与预期）。
- 最近评级变动：`grades`（机构、日期、动作、前后评级）。

## 6. 计算架构

```
每晚批量（北京时间约 06:30，排在美股雷达预热之后；只跑美股 + A 股预期快照）
  ├─ 拉取：标普1500 × {收盘价序列(light), 一致预期}；有新财报的公司重拉季度利润表 / 现金流 / 资产负债
  ├─ 计算：原始指标 → 板块分布 → 百分位/等级(含防抖) → 维度分 → 综合分/一票否决 → 阶段 → 文案
  └─ 落库 Postgres → 预热 Redis
请求 GET /quant-research/us/{symbol}
  ├─ 样本内 → 读当日结果（Redis → Postgres）
  └─ 样本外 → 现拉约 6 个接口 → 按当日板块分布打分 → Redis 缓存 1 天
```

- 服务分层：`app/services/quant_research/`（纯函数：指标、百分位、等级、聚合、阶段、文案；编排：batch、on-demand）；`app/schemas/quant_research.py`；Redis 操作放 `app/cache/`；DB 操作走 `get_db()`。
- 数据表（继承 `UUIDModel`，alembic autogenerate）：

| 表 | 内容 |
|---|---|
| `quant_fundamental_snapshot` | 股票 × 最新季度 TTM 财务（利润表 / 现金流 / 资产负债关键项）+ 财报期与披露日；仅披露新财报后更新 |
| `quant_estimate_snapshot` | 日期 × 市场 × 股票 × 财年：EPS / 营收 / EBITDA / EBIT 一致预期均值、高低值、分析师数（**EPS 修正依赖；A 股同表 market=cn**） |
| `quant_sector_distribution` | 日期 × 板块 × 指标：排序后的数值数组（样本外打分、P10~P90） |
| `quant_result` | 日期 × 股票：完整结果 JSON + 各层等级（防抖需要上一日等级；以后做等级历史、回测不用重算） |

- 存档必须是**当时可见的数据**（point-in-time），不得用事后修订值覆盖历史，保证日后回测可信。
- **首份快照导入**：上线时把 `data/quant_seed/2026-09-30/raw/*.est.json`（标普1500 全部一致预期，2026-09-30 拉取）作为 `quant_estimate_snapshot` 的第一天写入，EPS 修正积累期从 2026-09-30 起算；导入脚本幂等，只补不覆盖。
- 成分表：维基百科每周刷新，结果存 Redis（带 TTL）。

## 7. FMP 调用预算与稳定性

- 套餐上限实测 **300 次/分钟**（满负荷时稳定 300/分钟成功）。
- 新增**全局限流器**（Redis 令牌桶，跨进程共享，`app/cache/operations.py`）；量化研究与分析师评级的所有 FMP 调用都经过它。现有模块（雷达、缠论等）预留接入点，逐步迁移。
- **夜间批量 ≤ 150 次/分钟**；出现任一 429 → 批量整体暂停 2 分钟（熔断）；用户实时请求不受批量配额约束。
- 每日调用量：收盘价 ~1500 + 一致预期 ~1500 + 新财报公司报表（财报季数百）≈ 3000–3500 次 → 约 20–25 分钟。
- 失败处理：单只股票失败沿用上次数据并如实标注 `as_of` 旧日期；整批失败接口返回前一日结果（日期可见）；板块样本 < 20 的指标记「样本不足」不参与。
- 教训（本次设计过程中）：一次性脚本与线上共用 key、8 并发打满配额，曾造成线上 FMP 请求被限流约 8 分钟。任何批量 / 研究脚本都必须限速并留足线上余量。
